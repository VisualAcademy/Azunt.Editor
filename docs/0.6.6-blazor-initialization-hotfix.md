# Azunt.Editor 0.6.6 — Blazor initialization / Export reliability hotfix

## Why

The shared `azunt-editor.js` previously called `mountAll()` on `DOMContentLoaded` for **every** editor, including Blazor Server editors that were still prerendered. `mount()` changes toolbar markup and binds event handlers. Blazor later makes the same prerendered page interactive, which can replace the DOM and create an initialization-order race. Depending on timing, UI controls could appear ready even though Blazor events or host-provided Export commands were not yet bound. This is a lifecycle risk confirmed by source review; the exact reported host-side failure cannot be conclusively attributed without an actual Blazor Server trace.

## Fix

- The Blazor component uses internal `EditorMarkup.RenderForBlazor`, which includes `data-azunt-mount="manual"`. The existing public `EditorMarkup.Render(...)` signature and its MVC/Razor Pages automatic mounting behavior are unchanged.
- `AzuntEditor.mountAll()` skips manual-mode elements. Interactive Blazor mounts its instance from `OnAfterRenderAsync`, supplying the `.NET` callback reference before registering Export commands.
- The Blazor component applies a pending Mode change after its first mount. The sample's Switch button now changes the `Mode` parameter only; it avoids a duplicate direct JS call while mounting.
- The Blazor sample uses `@Assets[...]` for the editor and export CSS/JS files so the .NET static asset mapping can resolve fingerprinted URLs. The MVC/Razor Pages layout adds `asp-append-version="true"` to the referenced RCL CSS/JS assets.
- A browser regression test models a prerendered editor and a separate MVC editor, then simulates Blazor DOM replacement followed by mount and repeated View/Edit and Export operations.

## Verify on the actual .NET 10 host

1. Apply this patch over the **0.6.6** source, rebuild, restart the server, and open `/editor/blazor` in a new tab.
2. Without refreshing, click **Switch to View** and **Switch to Edit**. Verify both react and the document is preserved.
3. Open **Export** on initial page load and after at least three mode roundtrips; confirm PDF/Word/Excel commands appear and invoke their handlers **once**.
4. Navigate among MVC, Razor Pages, and Blazor examples and confirm all editors are interactive. Test direct `/editor/blazor?mode=view` initialization as well.
5. Open DevTools → Network: verify the `_content/Azunt.Editor` and `_content/Azunt.Editor.Export` JS/CSS requests succeed, examine their resolved URLs, and look for stale cached responses.
6. If the symptom recurs, capture Console errors, `_blazor` WebSocket/SignalR connection status, the first failed request in Network, and the server log. This distinguishes the editor initialization bug from a Blazor circuit disconnect.
7. Test an actual PDF download separately. This fix targets command wiring and initialization, not Playwright/browser installation.

## Checks performed in this environment

- Chromium browser tests of prerender mount isolation, MVC auto-mount, Edit/View roundtrips, Export command invocation, and idempotent remount.
- Existing Chromium editor and UI regression scripts, plus JavaScript parse, CSS namespace, package policy, and JS interop static checks.
- **Not performed:** .NET 10 build, actual InteractiveServer host connection test, or PDF generation, because the .NET SDK and target Windows host are unavailable here.
